# ТЕХНІЧНЕ ЗАВДАННЯ

**Проєкт:** Вебсистема онлайн-замовлень у кав'ярні (Optima Coffee)  
**Команда:** Компанія 2 (Студентська команда розробки)  
**Версія документа:** 1.0 від 12.09.2026  

---

## 1 Загальний опис проєкту

### 1.1 Мета й завдання

Метою проєкту є створення надійної, швидкої та зручної вебсистеми попереднього замовлення страв та напоїв у кав'ярні для усунення фізичних черг у години пікового навантаження, пришвидшення обслуговування клієнтів (take-away) та надання персоналу кав'ярні зручного інструменту оперативного керування асортиментом і чергою замовлень.

**Вимірювані бізнес-цілі:**
- Скорочення часу очікування клієнтом готового замовлення біля стійки до менш ніж 1 хвилини.
- Забезпечення оформлення замовлення користувачем менш ніж за 45 секунд.
- Зниження навантаження на бариста під час прийому замовлень у пікові години мінімум на 30%.

### 1.2 Цільова аудиторія

| Персона | Вік / роль | Цілі | Проблеми (pain points) | Технічні навички |
|---|---|---|---|---|
| Олексій (Гість) | 26 років, IT-фахівець | Швидко взяти каву перед початком робочого дня без черги | Черги біля каси, невідомий точний час очікування напою | Впевнений користувач смартфонів та вебсервісів |
| Марія (Бариста) | 22 роки, бариста кав'ярні | Чітко бачити послідовність замовлень та оперативно позначати відсутні позиції | Плутанина з паперовими чеками, відволікання на прийом оплати | Базові навички роботи з планшетом / веббраузером |

### 1.3 Межі проєкту

**Входить в обсяг MVP:**
- Реєстрація, автентифікація та авторизація користувачів (JWT, збереження сесії, захист паролів).
- Каталог меню страв та напоїв з категоріями, реальними цінами, фотографіями та алергенами.
- Інтерактивний кошик з інлайн-зміною кількості `+/-`, вибором бажаного часу самовивозу та побажань.
- Створення та відстеження статусу замовлення клієнтом (`pending`, `preparing`, `ready`, `completed`, `cancelled`).
- Панель керування для бариста та адміністратора (миттєвий стоп-лист страв, редагування меню, жива черга замовлень з перемиканням статусів).
- Контейнеризація в Podman Compose (сервіси db, backend, frontend).

**Не входить в обсяг MVP (перспективи розвитку):**
- Інтеграція фіскального реєстратора (ПРРО).
- Онлайн-еквайринг банківськими картками через LiqPay / WayForPay.
- Push-сповіщення у мобільному застосунку та Telegram-бот для клієнтів.

## 2 Вимоги

### 2.1 Функціональні вимоги

| ID | Вимога | Пріоритет (MoSCoW) | Критерій приймання |
|---|---|---|---|
| FR-01 | Користувач має можливість зареєструвати обліковий запис з email та паролем | Must | Статус 201 Created, пароль збережено у вигляді bcrypt-хешу, автоматичний вхід |
| FR-02 | Користувач має можливість увійти в систему за допомогою email та пароля | Must | Статус 200 OK, повернення валідного JWT токена доступу |
| FR-03 | Користувач має можливість переглядати каталог меню з категоріями та цінами | Must | Статус 200 OK, перелік доступних позицій з фотографіями, описами, цінами та алергенами |
| FR-04 | Користувач має можливість додавати позиції до кошика та змінювати кількість | Must | Збереження стану в браузері, реактивне оновлення суми замовлення, кнопки `+/-` |
| FR-05 | Користувач має можливість оформити замовлення із зазначенням часу самовивозу | Must | Створення запису в базі даних, статус `pending`, відображення замовлення в історії |
| FR-06 | Користувач має можливість відстежувати статус виконання свого замовлення | Should | Відображення статусу в реальному часі (`pending` -> `preparing` -> `ready` -> `completed`) |
| FR-07 | Бариста/Адміністратор має можливість перемикати доступність страв (стоп-лист) | Must | Ендпоїнт `PATCH /menu/items/{id}/availability`, миттєве блокування замовлення відсутньої позиції |
| FR-08 | Бариста має можливість переглядати чергу замовлень та змінювати їхні статуси | Must | Спеціалізована панель бариста, фільтрація замовлень, переведення статусу одним кліком |

### 2.2 Нефункціональні вимоги

| ID | Категорія | Вимога (вимірювана) | Спосіб перевірки |
|---|---|---|---|
| NFR-01 | Продуктивність | Час відгуку API на читання меню не перевищує 50 мс за нормального навантаження | Навантажувальне тестування, метрики часу відповіді |
| NFR-02 | Безпека | Паролі хешуються за алгоритмом bcrypt, захищені ендпоїнти перевіряють JWT | Аналіз коду, тести безпеки pytest (401/403) |
| NFR-03 | Надійність | База даних зберігає дані на іменованому томі Podman при перезапуску контейнерів | Рестарт контейнера `coffee_db`, збереження записів |
| NFR-04 | Зручність | Інтерфейс клієнта адаптований під мобільні екрани (360px+) та ПК (1920px) | Кросбраузерне тестування, мобільний емулятор |
| NFR-05 | Масштабованість | Архітектура трирівнева, бізнес-логіка ізольована від HTTP-шару | Відповідність layer rules (api -> services -> repositories) |

## 3 Архітектура й технології

### 3.1 Архітектура системи
Система побудована за трирівневою тришаровою архітектурою (Three-Tier Architecture):
- **Рівень представлення (Client/Frontend)**: Vanilla JavaScript (ES6+), HTML5, CSS3, компонентна структура.
- **Рівень прикладного шлюзу та логіки (Backend API)**: Python, FastAPI, Pydantic DTOs, Service layer, Repository layer.
- **Рівень збереження даних (Database)**: PostgreSQL 16 з міграціями SQLAlchemy 2.0.

Архітектурні рішення задокументовано в ADR:
- [ADR-0001: Архітектурний стиль](adr/0001-three-tier-architecture-style.md)
- [ADR-0002: Вибір стеку бекенду](adr/0002-backend-language-and-framework.md)
- [ADR-0003: Відхилення мови Go](adr/0003-second-backend-language-go-evaluation.md)
- [ADR-0004: Вибір СУБД PostgreSQL](adr/0004-database-engine-postgresql.md)
- [ADR-0005: Контейнеризація Podman](adr/0005-container-runtime-podman-and-persistence.md)
- [ADR-0006: Стратегія розгалуження](adr/0006-branching-strategy.md)

### 3.2 Технологічний стек

| Компонент | Технологія | Обґрунтування | Відхилені альтернативи |
|---|---|---|---|
| Backend | Python 3.11+, FastAPI | Висока продуктивність на базі Starlette/uvicorn, автоматична OpenAPI-документація, сувора валідація Pydantic | Django, Flask, Express.js |
| ORM | SQLAlchemy 2.0 | Зрілий ORM з повною типізацією, Data Mapper патерн, безпека від SQL-ін'єкцій | Tortoise ORM, сирий SQL |
| База даних | PostgreSQL 16 | Реляційна цілісність даних, висока надійність ACID, підтримка JSONB | MySQL, MongoDB, SQLite |
| Frontend | Vanilla JavaScript, HTML5, CSS3 | Відсутність зайвих залежностей, швидке завантаження, контроль стану | React, Vue.js, Angular |
| Контейнеризація | Podman + Podman Compose | Rootless безпека без демона root, сумісність з OCI-стандартами | Docker, Docker Swarm |

### 3.3 Модель даних
Основні сутності реляційної моделі:
- **`users`**: `id`, `email`, `hashed_password`, `full_name`, `phone`, `is_active`, `is_superuser`, `created_at`.
- **`categories`**: `id`, `name`, `description`, `sort_order`, `is_active`, `created_at`.
- **`menu_items`**: `id`, `category_id`, `name`, `description`, `price`, `image_url`, `is_available`, `allergens`, `created_at`.
- **`orders`**: `id`, `user_id`, `status`, `total_amount`, `pickup_time`, `customer_notes`, `created_at`.
- **`order_items`**: `id`, `order_id`, `menu_item_id`, `quantity`, `unit_price`.

## 5 Критерії приймання продукту

1. Усі функціональні вимоги категорії Must (FR-01 — FR-08) реалізовано та протестовано.
2. 100% модульних та інтеграційних тестів бекенду (50 тестів) проходять успішно без помилок.
3. Лінтер `ruff check .` та форматер не виявляють помилок у кодовій базі.
4. Документація OpenAPI 3.1 актуальна та відповідає всім зареєстрованим маршрутам.
5. Система розгортається однією командою `podman-compose -f deploy/podman-compose.yml up -d` на чистій системі.
