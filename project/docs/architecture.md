# АРХІТЕКТУРА ПРОГРАМНОЇ СИСТЕМИ (ARCHITECTURE DESCRIPTION)

**Проєкт:** Вебсистема онлайн-замовлень у кав'ярні (Optima Coffee)  
**Архітектурний стиль:** Three-Tier Architecture (Трирівнева тришарова архітектура)  
**Статус:** Accepted (ADR-0001)  

---

## 1 Загальний огляд архітектури

Система реалізована за класичним трирівневим підходом із суворою ізоляцією шарів відповідальності:
1. **Клієнтський рівень (Client Tier)**: Легковаговий односторінковий застосунок (SPA) на чистому сучасному JavaScript (ES6+), HTML5 та модульному CSS. Відповідає виключно за рендеринг інтерфейсу, обробку взаємодії користувача та роботу з локальним станом кошика.
2. **Серверний рівень (Backend API Tier)**: Модульний вебсервіс на Python 3.11+ та фреймворку FastAPI. Включає HTTP-маршрутизацію (API Layer), бізнес-логіку (Service Layer), рівень доступу до даних (Repository Layer) та крос-компонентні механізми автентифікації й RBAC.
3. **Рівень збереження даних (Database Tier)**: Реляційна СУБД PostgreSQL 16, що працює в ізольованому контейнері з монтуванням іменованого тому для гарантії збереження даних.

Діаграма компонентної моделі наведена у файлі [`docs/architecture.puml`](architecture.puml).

## 2 Обов'язки компонентів

| Рівень / Модуль | Основні обов'язки | Технології |
|---|---|---|
| Frontend UI Components | Рендеринг карток меню, кошика, панелі замовлень бариста, модальних вікон | Vanilla JS, CSS3, Semantic HTML |
| API Client | Ізольований модуль взаємодії з REST API, керування Bearer токенами | Fetch API, LocalStorage |
| API Endpoints | Валідація вхідних даних (Pydantic DTO), HTTP-статуси, маршрутизація | FastAPI, Pydantic v2 |
| Security / RBAC | Хешування паролів, генерація та перевірка JWT, перевірка `is_superuser` | Passlib (bcrypt), PyJWT |
| Service Layer | Бізнес-правила (розрахунок суми, зміна статусів, перевірка доступності у стоп-листі) | Чистий Python (без прив'язки до вебфреймворку) |
| Repository Layer | Побудова SQL-запитів, виконання транзакцій, робота з моделями ORM | SQLAlchemy 2.0 |
| Database | Збереження таблиць `users`, `categories`, `menu_items`, `orders`, `order_items` | PostgreSQL 16 |

## 3 Потік обробки запитів (Request Flow)

Потік виконання запиту в системі є односпрямованим і суворо відповідає правилу:
`Користувач -> Web-клієнт -> API Endpoints -> Service Layer -> Repository Layer -> PostgreSQL`

1. Клієнт формує HTTP-запит (наприклад, `POST /api/v1/orders`) із JSON-тілом та заголовком `Authorization: Bearer <token>`.
2. Залежність `get_current_user` перевіряє валідність підпису токена та завантажує профіль користувача.
3. Роутер перевіряє відповідність DTO `OrderCreate` за допомогою схем Pydantic.
4. Роутер делегує виконання методу `OrderService.create_order`.
5. Сервіс перевіряє актуальну доступність кожної замовленої страви у стоп-листі та формує сутність замовлення.
6. Репозиторій зберігає дані в рамках єдиної транзакції бази даних.
7. Відповідь повертається клієнту у форматі DTO `OrderResponse` з кодом 201 Created.

## 4 Нефункціональні характеристики системи

- **Модульність:** Чіткі межі між шарами дозволяють замінити базу даних або інтерфейс клієнта без модифікації бізнес-правил у сервісах.
- **Масштабованість:** Безсесійний (stateless) дизайн бекенду на основі JWT токенів дозволяє горизонтально масштабувати екземпляри `coffee_backend` за реверс-проксі.
- **Безпека:** Застосування параметризованих ORM-запитів виключає SQL-ін'єкції; паролі користувачів захищені сучасним криптографічним хешуванням bcrypt.
- **Надійність:** Використання контейнеризації Podman та іменованого тому `pgdata` забезпечує стійкість системи до перезапусків та оновлень контейнерів.
