# АРХІТЕКТУРА ПРОГРАМНОЇ СИСТЕМИ (ARCHITECTURE DESCRIPTION)

**Проєкт:** Вебсистема онлайн-замовлень у кав'ярні (Optima Coffee)  
**Архітектурний стиль:** Three-Tier Architecture (Трирівнева тришарова архітектура)  
**Статус:** Accepted (ADR-0001)  

---

## 1 Загальний огляд архітектури

Система реалізована за класичним трирівневим підходом із суворою ізоляцією шарів відповідальності:
1. **Клієнтський рівень (Client Tier)**: Легковаговий односторінковий застосунок (SPA) на чистому сучасному JavaScript (ES6+), HTML5 та модульному CSS. Відповідає виключно за рендеринг інтерфейсу, обробку взаємодії користувача та роботу з локальним станом кошика.
2. **Серверний рівень (Backend API Tier)**: Модульний вебсервіс на Python 3.12+ та фреймворку FastAPI. Включає HTTP-маршрутизацію (API Layer), бізнес-логіку (Service Layer), рівень доступу до даних (Repository Layer) та крос-компонентні механізми автентифікації й RBAC.
3. **Рівень збереження даних (Database Tier)**: Підтримує дуальну стратегію збереження даних (ADR-0004, ADR-0010):
   - **PostgreSQL 16**: Промислова реляційна СУБД для багатоконтейнерних середовищ (Podman Compose, Google Cloud SQL) із збереженням даних в іменованих томах.
   - **SQLite**: Автономний вбудований рушій із нульовою конфігурацією (Zero-Config), автоматичним сідінгом структури і даних при старті, оптимізований для автономних Docker-образів та хмарних інстансів з обмеженою пам'яттю (AWS EC2 `t3.micro`).

Діаграма компонентної моделі наведена у файлі [`docs/architecture.puml`](architecture.puml).

## 2 Обов'язки компонентів

| Рівень / Модуль | Основні обов'язки | Технології |
|---|---|---|
| Frontend UI Components | Рендеринг карток меню, кошика, панелі замовлень бариста, модальних вікон | Vanilla JS, CSS3, Semantic HTML |
| API Client | Ізольований модуль взаємодії з REST API, динамічний відносний URL, токени | Fetch API, LocalStorage |
| API Endpoints | Валідація вхідних даних (Pydantic DTO), HTTP-статуси, маршрутизація, роздача статики | FastAPI, Pydantic v2 |
| Security / RBAC | Хешування паролів, генерація та перевірка JWT, перевірка `is_superuser` | Passlib (bcrypt), PyJWT |
| Service Layer | Бізнес-правила (розрахунок суми, зміна статусів, перевірка доступності у стоп-листі) | Чистий Python (без прив'язки до вебфреймворку) |
| Repository Layer | Побудова SQL-запитів, виконання транзакцій, робота з моделями ORM | SQLAlchemy 2.0 |
| Database Tier | Збереження таблиць `users`, `categories`, `menu_items`, `orders`, `order_items` | PostgreSQL 16 / SQLite (Zero-Config) |

## 3 Потік обробки запитів (Request Flow)

Потік виконання запиту в системі є односпрямованим і суворо відповідає правилу:
`Користувач -> Web-клієнт -> API Endpoints -> Service Layer -> Repository Layer -> PostgreSQL`

1. Клієнт формує HTTP-запит (наприклад, `POST /api/v1/orders`) із JSON-тілом та заголовком `Authorization: Bearer <token>`.
2. Залежність `get_current_user` перевіряє валідність підпису токена та завантажує профіль користувача.
3. Роутер перевіряє відповідність DTO `OrderCreate` за допомогою схем Pydantic.
4. Роутер делегує виконання методу `OrderService.create_order`.
5. Сервіс перевіряє актуальну доступність кожної замовленої страви у стоп-листі та формує сутність замовлення.
6. Репозиторій зберігає дані в рамках єдиної транзакції бази даних.
7. Відповідь повертається клієнту у форматі DTO `OrderResponse` з кодом 201 Created.

## 4 Нефункціональні характеристики системи

- **Модульність:** Чіткі межі між шарами дозволяють замінити базу даних (PostgreSQL ↔ SQLite) або інтерфейс клієнта без модифікації бізнес-правил у сервісах.
- **Масштабованість:** Безсесійний (stateless) дизайн бекенду на основі JWT токенів дозволяє горизонтально масштабувати екземпляри сервісу за балансувальником або в Cloud Run.
- **Безпека:** Застосування параметризованих ORM-запитів виключає SQL-ін'єкції; паролі захищені хешуванням bcrypt; секрети ізольовані у GitHub Secrets та змінних середовища.
- **Ефективність використання ресурсів:** Підтримка автономного SQLite-режиму зі споживанням пам'яті ~70–90 МБ дозволяє системі стабільно функціонувати навіть на мінімальних хмарних інстансах AWS EC2 `t3.micro` (1 ГБ RAM) без ризику OOM.

## 5 Топології розгортання та CI/CD автоматизація (ADR-0009, ADR-0010)

Система підтримує три взаємодоповнюючі топології розгортання:

### Топологія 1. Автономне хмарне розгортання в AWS EC2 (IaC + CI/CD)
- **Інфраструктура:** Віртуальна машина AWS EC2 (`t3.micro`, AMI `ami-0705384c0b33c194c`, регіон `eu-north-1`), описана як код у директорії `infra/` за допомогою Terraform.
- **Контейнеризація:** Єдиний уніфікований OCI/Docker контейнер, що містить і бекенд (FastAPI), і роздачу оптимізованого статичного фронтенду на порті 8000.
- **База даних:** Вбудована SQLite з нульовою конфігурацією та автоматичним сідінгом демо-меню, замовлень і доступу для бариста при кожному старті.
- **Безперервна доставка:** Автоматизований GitHub Actions конвеєр (`ci.yml`):
  1. *Backend Checks:* Лінтер Ruff, 50 тестів Pytest, валідація OpenAPI специфікацій.
  2. *Docker Hub Build & Push:* Збірка образу та публікація у публічний реєстр.
  3. *Terraform Apply:* Автоматичне керування інфраструктурою AWS із автоімпортом стану.
  4. *Deploy over SSH:* Оновлення контейнера на EC2 та валідація життєздатності через `/health`.

### Топологія 2. Серверлес-розгортання в Google Cloud Run
- **Архітектура:** Роздільні незалежні сервіси для бекенду (`optima-coffee-backend`) та фронтенду (`optima-coffee-frontend`) під керуванням Google Cloud Run.
- **База даних:** Керована реляційна СУБД Google Cloud SQL for PostgreSQL 16 із захищеним підключенням через Cloud SQL Auth Proxy.

### Топологія 3. Локальна мультиконтейнерна розробка (Podman Compose)
- **Архітектура:** Три ізольовані сервіси (`coffee_db`, `coffee_backend`, `coffee_frontend`).
- **База даних:** PostgreSQL 16 із монтуванням персистентного іменованого тому `coffee_shop_pgdata`.
