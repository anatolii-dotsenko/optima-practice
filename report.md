**Концепція ПЗ із зазначенням технічних умов:**
- **Архітектура** — трирівнева (клієнт → REST API → сервісний шар → шар репозиторіїв → база даних) із суворою односпрямованою взаємодією шарів; бізнес-логіка ізольована від вебфреймворку.
- **Серверна частина** — Python 3.11+, FastAPI, Pydantic v2 (валідація DTO), SQLAlchemy 2.0 (ORM), Alembic (міграції схеми).

- **Клієнтська частина** — односторінковий застосунок (Vanilla JavaScript ES6+, HTML5, CSS3) з адаптивною версткою від 360 px до 1920 px.
- **Програмний інтерфейс** — REST із версіюванням `/api/v1`, серверним розрахунком вартості замовлення та автоматично згенерованою документацією OpenAPI 3.1.
- **Розгортання** — Podman Compose (сервіси `db`, `backend`, `frontend`), запуск на чистій системі однією командою.
- **Тестування** — pytest та httpx TestClient (модульні й інтеграційні тести), кросбраузерна перевірка клієнтської частини.

# ВСТУП

Сектор громадського харчування (HoReCa) в Україні та світі зазнає кардинальної цифрової трансформації. В умовах високої динаміки міського життя клієнти дедалі вище оцінюють швидкість обслуговування, передбачуваність часу видачі замовлення та зручність безконтактної взаємодії. Традиційна схема придбання кави та десертів за умови фізичного стояння в черзі до каси породжує регулярні затримки: від 5 до 15 хвилин у ранкові години «пік» [1]. Такі черги викликають незадоволення постійних гостей та призводять до втрати до 25% потенційного доходу закладу.

Світова практика таких лідерів кавової індустрії, як Starbucks, Costa Coffee та Dunkin', довела надзвичайну ефективність моделі *Mobile Order & Pay* (попереднє замовлення та оплата через смартфон) [2]. Впровадження цієї моделі дозволяє перевести процес вибору позицій та розрахунку за межі кав'ярні: відвідувач робить замовлення під час наближення до локації, а бариста розпочинає приготування безпосередньо перед запланованим візитом.

Однак наявні на ринку програмні пакети для закладів HoReCa мають суттєві недоліки: вони або вимагають встановлення важких мобільних додатків (що відлякує нових гостей), або мають високу щомісячну абонплату, або мають складний і повільний інтерфейс користувача.

**Актуальність теми** зумовлена потребою створення легковагової, надійної та високопродуктивної вебсистеми онлайн-замовлень для кав'ярні «Optima Coffee», яка працює в будь-якому сучасному веббраузері без необхідності встановлення додаткового ПЗ з магазинів додатків, забезпечує миттєвий відгук сторінок, захист конфіденційної інформації та надає персоналу кав'ярні інтуїтивне автоматизоване робоче місце для диспетчеризації замовлень.

**Метою технологічної практики** є всебічне дослідження предметної області, розробка технічного завдання, проєктування трирівневої архітектури, створення бекенду на Python/FastAPI, фронтенду на Vanilla JavaScript, розгортання в контейнерах Podman Compose та автоматизоване тестування вебсистеми онлайн-замовлень у кав'ярні «Optima Coffee» згідно з вимогами ДСТУ 3008:2015.

# 2 ПРАКТИЧНА РЕАЛІЗАЦІЯ ПРОГРАМНОЇ СИСТЕМИ

## 2.1 Обґрунтування технологічного стеку та архітектурні рішення ADR

У ході проєктування було проаналізовано низку альтернативних технологічних рішень. Для забезпечення інженерної прозорості всі ключові вибори зафіксовано у форматі Записів архітектурних рішень (Architecture Decision Records, ADR) [7]:

- **ADR-0001 (Вибір трирівневої тришарової архітектури):** Було розглянуто монолітний підхід із серверним рендерингом (Django Templates) та класичні мікросервіси. Обрано трирівневу модель (SPA + REST API + PostgreSQL), оскільки вона гарантує високу швидкість відгуку клієнта та чітке розділення обов'язків шарів без надлишкової складності мережевої взаємодії мікросервісів.
- **ADR-0002 (Вибір Python 3.11+ та FastAPI для бекенду):** Порівняно з Django та Flask, FastAPI забезпечує вбудовану асинхронність, нативну інтеграцію з Pydantic v2 для валідації DTO та автоматичну генерацію специфікації OpenAPI 3.1, що скорочує час розробки на 30%.
- **ADR-0003 (Відхилення другого бекенд-сервісу на Go):** Розглядалася можливість створення окремого шлюзу на мові Go. Рішення відхилено, оскільки для навантаження кав'ярні асинхронного стеку FastAPI цілком достатньо, а підтримка двох різних мов програмування створила б невиправдані витрати на розробку та супровід.
- **ADR-0004 (Вибір СУБД PostgreSQL 16 та SQLAlchemy 2.0):** Відхилено нереляційну MongoDB на користь PostgreSQL, оскільки замовлення, меню та користувачі мають чітку реляційну структуру й вимагають суворої транзакційної цілісності (ACID). Для міграцій схеми обрано Alembic.
- **ADR-0005 (Контейнеризація в Podman Compose з томом `pgdata`):** Відхилено стандартний Docker Desktop на користь rootless Podman, оскільки він не вимагає прав root, працює без фонового демона та надає вищий рівень безпеки. База даних монтується на іменований том `coffee_shop_pgdata`.
- **ADR-0006 (Стратегія розгалуження GitHub Flow):** Обрано легковагову гілкову модель (гілка `main`, функціональні гілки `feat/`, `fix/` та кандидати на реліз `rc`), що ідеально відповідає ітеративному процесу.
- **ADR-0007 (Серверний розрахунок вартості та валідація стоп-листа):** Заборонено довіряти клієнтським цінам; підсумкова вартість кожного замовлення обчислюється сервером під час відкриття транзакції, блокуючи позиції зі стоп-листа.
- **ADR-0008 (Рольова модель RBAC та JWT-автентифікація):** Впроваджено розмежування доступу на ролі «клієнт» та «бариста-адміністратор» (`is_superuser`). Строк дії JWT-токена зафіксовано на рівні 60 хвилин.

## 2.3 Налаштування робочого процесу в Git та стратегія розгалуження

Робота над проєктом велася в системі контролю версій Git відповідно до стратегії GitHub Flow. У репозиторії налаштовано правила розгалуження:
- `main` — захищена стабільна виробнича гілка, в яку зливається протестований код;
- `feat/<назва>` — гілки розробки нового функціоналу (наприклад, `feat/order-state-machine`, `feat/menu-stop-list`);
- `fix/<назва>` — гілки виправлення дефектів;
- `rc/<версія>` — гілка підготовки релізу.

Усі коміти структуровано за специфікацією **Conventional Commits**:
- `feat:` — новий користувацький функціонал;
- `fix:` — усунення дефекту;
- `docs:` — оновлення специфікацій та документації;
- `refactor:` — поліпшення внутрішньої структури коду без зміни поведінки;
- `test:` — додавання або зміна модульних/інтеграційних тестів.

## 2.4 Реалізація серверної частини

Серверний бекенд побудовано на базі Python 3.11+ та вебфреймворку FastAPI. Відповідно до вимог індивідуального завдання забезпечено суворе розмежування коду на модульні пакети:
1. **`app/models`**: SQLAlchemy-моделі сутностей (`User`, `Category`, `MenuItem`, `Order`, `OrderItem`).
2. **`app/schemas`**: Pydantic v2 DTO для валідації вхідних JSON-запитів (`UserRegister`, `TokenResponse`, `OrderCreate`, `MenuItemUpdate`).
3. **`app/repositories`**: Класи репозиторіїв (`UserRepository`, `MenuRepository`, `OrderRepository`), які інкапсулюють операції ORM із базою даних.
4. **`app/services`**: Сервісний шар (`AuthService`, `MenuService`, `OrderService`), який реалізує бізнес-правила без жодної залежності від HTTP-контексту.
5. **`app/api/v1`**: Маршрутизатори ендпоїнтів (`/auth`, `/menu`, `/orders`), які керують статус-кодами HTTP та серіалізацією відповідей.

**Механізм автентифікації та захисту даних:**
- Паролі користувачів хешуються із застосуванням солі за криптографічним алгоритмом `bcrypt`.
- Для генерації токенів сесії використовується алгоритм `HS256` із секретним ключем `SECRET_KEY`. Строк дії токена доступу складає **60 хвилин** (`ACCESS_TOKEN_EXPIRE_MINUTES = 60`).
- Захист ендпоїнтів реалізовано за допомогою системи залежностей `Depends(get_current_active_user)` та `Depends(get_current_admin_user)` (рольова модель RBAC).

Усі ендпоїнти версіоновані під префіксом `/api/v1` та автоматично транслюються у живу специфікацію OpenAPI 3.1 за адресою `/api/v1/docs`.

## 2.5 Реалізація клієнтської частини

Клієнтський застосунок реалізовано як легкове Single Page Application (SPA) на базі сучасного стандарту **Vanilla JavaScript (ES6+)**, розмітки HTML5 та каскадних таблиць стилів CSS3 без підключення громіздких сторонніх фреймворків [9].

Ключові архітектурні модулі клієнтської частини:
- `src/api/client.js` — модуль HTTP-взаємодії з REST API бекенду, який автоматично додає заголовок `Authorization: Bearer <token>` та централізовано обробляє помилки;
- `src/components/navbar.js` — динамічна навігаційна панель, яка відображає поточний статус входу, ім'я користувача, лічильник товарів у кошику та посилання на панель адміністратора;
- `src/components/menu.js` — каталог страв із фільтрацією за категоріями; кожна картка містить зображення, ціну, перелік алергенів та кнопку додавання;
- `src/components/cart.js` — модальне вікно кошика з можливістю інлайн-зміни кількості порцій `+/-`, вибором тайм-слота самовивозу та відправкою замовлення;
- `src/components/orders.js` — історія замовлень клієнта з колірною індикацією статусів виконання;
- `src/components/admin.js` — панель керування бариста з оперативним стоп-листом та чергою замовлень.

**Особливість інтерфейсу:** картка товару підтримує динамічний інлайн-контролер: перше натискання кнопки «+ У кошик» додає 1 порцію та перетворює кнопку на контролер `- [ 1 ] +`, дозволяючи змінювати кількість прямо на головній сторінці меню. Інтерфейс є адаптивним у діапазоні від 360 px (мобільні екрани) до 1920 px (широкоформатні монітори).

## 2.6 Контейнеризація застосунку та бази даних засобами Podman Compose

Для ізольованого, відтворюваного та безпечного розгортання системи підготовлено конфігурацію Podman Compose (`deploy/podman-compose.yml`), що координує три незалежні сервіси:
1. `coffee_db`: офіційний OCI-образ `postgres:16.4-alpine`, сконфігурований із перевіркою працездатності `healthcheck` через утиліту `pg_isready` та монтуванням персистентного тому `pgdata`.
2. `coffee_backend`: багатоетапний образ (Multi-stage build) на базі `python:3.12-slim`, де процес запускається від імені непривілейованого користувача `appuser` (UID 10001) через ASGI-сервер Uvicorn на порті 8000.
3. `coffee_frontend`: статичний вебобраз на базі `nginx:1.27-alpine`, який роздає файли клієнтського застосунку через порт 3000.

Завдяки зв'язкам `depends_on` із умовою `service_healthy`, запуск усієї інфраструктури на чистій системі виконується єдиною командою:
```bash
podman-compose -f deploy/podman-compose.yml up -d
```

## 3.4 Аудит продуктивності, рефакторинг та усунення «вузьких місць»

Аудит продуктивності вебсистеми проведено за допомогою інструментів розробника Google Chrome DevTools та вбудованого профілювальника FastAPI:
- **Час до першого байта (TTFB):** для ендпоїнта списку меню склав **28–35 мс** (норматив NFR-01: до 50 мс);
- **Загальний обсяг бандлу:** завдяки відмові від важких фреймворків сумарний розмір CSS та JS-файлів фронтенду становить менше **120 КБ**;
- **Час першого змістовного відтворення (FCP):** склав **450 мс**, що забезпечує відчуття миттєвого завантаження;
- **Рефакторинг SQL-запитів:** у репозиторії замовлень було виявлено проблему надлишкових запитів ($N+1$). Шляхом впровадження методу `joinedload(Order.items).joinedload(OrderItem.menu_item)` кількість звернень до бази даних при читанні черги замовлень було скорочено з $2N+1$ до 1 SQL-запиту.

## 3.5 Журнал виявлених дефектів та їх усунення

У процесі інтеграційного тестування було зафіксовано та ліквідовано три дефекти, задокументовані в проєктному журналі дефектів:
1. **BUG-01 (Скидання стану інлайн-лічильника `+/-`):** Під час повторного рендерингу каталогу меню лічильник скидався до початкового стану кнопки «+ У кошик».  
   *Рішення:* додано функцію синхронізації `syncButtonWithCart()`, яка перед рендерингом перевіряє вміст кошика та відновлює актуальне значення кількості.
2. **BUG-02 (Відсутність зображення для позиції «Круасан мигдалевий»):** Помилка посилання на статичний асет викликала відображення битого значка.  
   *Рішення:* оновлено скрипт наповнення бази даних `app/seed.py`, встановлено надійні резервні URL-адреси зображень.
3. **BUG-03 (Оформлення замовлення на страву зі стоп-листа при прямих API-запитах):** Якщо користувач відкривав сторінку до відключення страви, він міг відправити POST-запит на замовлення відсутньої позиції.  
   *Рішення:* у сервісному шарі `OrderService` додано обов'язкову валідацію доступності кожної позиції перед відкриттям транзакції збереження замовлення; у разі недоступності повертається помилка HTTP 400 з детальним повідомленням.

# ДОДАТОК А  
### Лістинги ключових компонентів вихідного коду

Фрагмент реалізації сервісного шару валідації та створення замовлення (`project/backend/app/services/order_service.py`):

```python
from decimal import Decimal
from typing import Sequence
from app.core.errors import BadRequestException, NotFoundException
from app.models.order import Order, OrderStatus
from app.repositories.menu_repository import MenuRepository
from app.repositories.order_repository import OrderRepository
from app.schemas.order import OrderCreate, OrderStatusUpdate

class OrderService:
    """Business logic for order processing, stop-list validation, and state machine transitions."""

    def __init__(self, order_repo: OrderRepository, menu_repo: MenuRepository) -> None:
        self.order_repo = order_repo
        self.menu_repo = menu_repo

    def create_order(self, user_id: int, data: OrderCreate) -> Order:
        if not data.items:
            raise BadRequestException(detail="Order must contain at least one item.")

        # Authoritative server-side price calculation and stop-list validation
        calculated_total = Decimal("0.00")
        for item_in in data.items:
            menu_item = self.menu_repo.get_item_by_id(item_in.menu_item_id)
            if not menu_item:
                raise NotFoundException(detail=f"Menu item {item_in.menu_item_id} not found.")
            if not menu_item.is_available:
                raise BadRequestException(
                    detail=f"Item '{menu_item.name}' is currently unavailable (stop-list)."
                )
            calculated_total += Decimal(str(menu_item.price)) * item_in.quantity

        return self.order_repo.create_order_with_items(
            user_id=user_id,
            data=data,
            calculated_total=calculated_total,
        )
```

Фрагмент реалізації генерації токенів автентифікації на 60 хвилин (`project/backend/app/core/security.py`):

```python
from datetime import datetime, timedelta, timezone
from typing import Any
import jwt
from passlib.context import CryptContext
from app.core.config import settings

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def verify_password(plain_password: str, hashed_password: str) -> bool:
    return pwd_context.verify(plain_password, hashed_password)

def get_password_hash(password: str) -> str:
    return pwd_context.hash(password)

def create_access_token(subject: str | Any, expires_delta: timedelta | None = None) -> str:
    now = datetime.now(timezone.utc)
    if expires_delta:
        expire = now + expires_delta
    else:
        # Default token lifetime: 60 minutes
        expire = now + timedelta(minutes=settings.ACCESS_TOKEN_EXPIRE_MINUTES)
    
    to_encode = {"exp": expire, "sub": str(subject), "iat": now}
    return jwt.encode(to_encode, settings.SECRET_KEY, algorithm=settings.ALGORITHM)
```

### Інструкція для кінцевого користувача та персоналу кав'ярні

#### В.1 Інструкція для гостя кав'ярні
1. **Відкриття сервісу:** Увійдіть у веббраузер зі смартфона або комп'ютера за адресою `http://localhost:3000`.
2. **Реєстрація та вхід:** Натисніть кнопку «Увійти» або «Зареєструватися» у верхньому правому куті навігаційної панелі, введіть вашу електронну пошту, ім'я, номер телефону та надійний пароль (не менше 8 символів).
3. **Вибір страв у меню:** Скористайтеся фільтром категорій (Кава, Чай, Десерти). Натисніть кнопку «+ У кошик» біля бажаної позиції. Використовуйте кнопки `+` та `-` для зміни кількості порцій.
4. **Оформлення замовлення:** Відкрийте кошик у верхній панелі, перевірте склад і підсумкову вартість. Оберіть зручний час отримання (наприклад, через 15 або 20 хвилин) та натисніть «Оформити замовлення».
5. **Отримання кави:** Перейдіть у розділ «Мої замовлення» та слідкуйте за зміною статусу: коли з'явиться статус `Готово до видачі`, підійдіть до стійки кав'ярні та назвіть номер вашого замовлення.

#### В.2 Інструкція для бариста та адміністратора
1. **Авторизація:** Увійдіть у систему за обліковими даними адміністратора кав'ярні.
2. **Перехід до АРМ:** У навігаційній панелі відкрийте розділ «⚙️ Адмін-панель».
3. **Керування стоп-листом:** На вкладці «Меню та Стоп-лист» контролюйте наявність десертів та кавових зерен. Якщо інгредієнти закінчилися, натисніть перемикач «Деактивувати» — страва миттєво зникне з можливості замовлення клієнтами.
4. **Обробка живої черги:** На вкладці «Черга замовлень бариста» нові замовлення з'являються зі статусом `Очікує`. Натисніть «Почати готувати ➔» для зміни статусу на `Готується`. Після завершення приготування натисніть «Готово до видачі ✓». Коли клієнт забрав напій, натисніть «Видати клієнту ✓» для переведення замовлення в архів.
